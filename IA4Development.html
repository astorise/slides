Développer
avec l'IA

Ma méthodologie

Illustrée par 3 cas : Tachyon-Mesh HyperDeskVR Pulse-Engine

Sébastien ASTORI · 2026
Cette première partie présente ma méthodologie de travail avec plusieurs IA, illustrée par trois projets aux registres différents : un projet à blanc qui part de l'idée, un projet en conditions réelles qui gère crashs et régressions, et un projet exploratoire en terrain inconnu qui remonte un protocole par reverse-engineering.
🎯 Cadrage

Le vrai sujet

Ce n'est pas :
  • « comment construire un mesh FaaS »
  • « comment développer pour un Quest »
  • « comment rétro-ingénier un protocole Garmin »
C'est : comment travailler avec plusieurs IA sans friction.

Les trois projets sont des supports — ils servent à rendre les patterns tangibles.

Je le dis explicitement pour cadrer l'attention. Le détail technique des projets est volontairement secondaire : on s'arrêtera à chaque pattern, pas à chaque feature.
🗺️ Les 3 terrains

Trois registres, trois approches

🧪
Tachyon-Mesh
ex nihilo
Service mesh FaaS
Rust · WASM · OpenSpec Idée → spec → code
🎯
HyperDeskVR
en crise
Client RDP Quest 3
C++ · FreeRDP Code qui casse
🔍
Pulse-Engine
en exploration
Reverse-eng Garmin
Kotlin · BLE · protobuf Boîte noire → spec

Trois façons différentes de faire travailler les IA.

Tachyon part d'une idée pure, spécifie avant d'exécuter. HyperDeskVR part d'un bug qui casse un truc qui marchait, avec tout le rabbit hole que ça implique. Pulse-Engine part d'un APK inconnu qu'on démonte pour reconstruire un client autonome — sans savoir ce qu'on va trouver avant de le trouver.
⏱️ Les 3 rythmes

Chaque projet a sa cadence

🧪
Tachyon — linéaire idée → spec → code → archive → spec suivante
🎯
HyperDeskVR — cyclique en crise symptôme → hypothèse → fix → test → régression → recommencer
🔍
Pulse-Engine — en spirale capture → décodage → implémentation → capture → pivot → spec
→ La méthodologie doit s'adapter au rythme du projet, pas l'inverse.
Ces trois rythmes ne sont pas interchangeables. Essayer de faire du "spec-first" sur Pulse-Engine alors qu'on ne connaît pas le protocole serait une perte de temps. Essayer de faire du "exploratoire" sur Tachyon serait du brouillon perpétuel. La lecture du bon rythme est une compétence en soi.

— Pattern 1 —

Taxonomie des IA

Le bon agent pour la bonne tâche

Pattern 1 · Énoncé

Scribe ≠ Collègue

Une IA généraliste est un bon collègue, pas un bon scribe.
Une IA de code est un bon scribe, pas un bon collègue.

🧠 Idéation
Challenger, pivoter, structurer
→ Gemini, Claude chat
🛠️ Exécution
Appliquer, tester, commiter
→ Codex, Claude Code
Les forcer à inverser les rôles coûte cher.
C'est le pattern fondateur. Sur les trois projets, j'ai maintenu la séparation. Gemini/Claude chat pour la dialectique d'architecture, Codex/Claude Code pour l'exécution disciplinée. Les inversions ponctuelles ont toujours produit du mauvais travail.
Pattern 1 · Illustration

3 projets, 3 postures

Tachyon Gemini en collègue :

— Je vais injecter mes secrets via env! au build.
— ⚠️ Mauvaise pratique : strings sur le binaire les récupère en clair.

HyperDeskVR Claude Code en scribe :

xrAttachSessionActionSets double-attach détecté. Commit 9c8df70. CI run vert. APK installé. Camera grant.

Pulse-Engine Codex en scribe ET collègue :

Table Metric.type extraite de classes9.dex. 40 entrées. SPO2 absent → inférence : passe par HSAData, pas par le flux live.
Le cas Pulse-Engine est intéressant parce que le reverse-engineering brouille la frontière entre scribe et collègue. Codex tabule (scribe), mais il doit aussi inférer ce que chaque code numérique veut dire (collègue). La séparation stricte ne tient plus, mais la taxonomie reste utile pour savoir dans quel mode on est à chaque tour.
— Pattern 2 —

Format pivot
versionné

Le contrat entre agents

Pattern 2 · Énoncé

Un contrat stable ou ça diverge

Dès qu'on travaille avec plusieurs agents, il faut un contrat stable.

Sinon chaque agent réexplique tout, perd le contexte, diverge.

Le contrat doit être :

📝 Textuel
Markdown, YAML
🗃️ Versionnable
Git
✅ Validable
CLI ou schema
👁️ Lisible
humain et agent
C'est le pattern le plus important du lot. Sans format pivot, travailler à plusieurs agents revient à copier-coller du contexte en permanence. Mais ce qui m'a surpris au fil des trois projets, c'est que le format pivot a plusieurs moments d'utilisation — pas seulement en design.
Pattern 2 · 3 moments

Même outil, trois usages

Moment Projet Usage
Design-time Tachyon OpenSpec avant le code — contrat entre Gemini et Codex
Runtime (crise) HyperDeskVR « État des lieux » Markdown produit pendant une crise pour handoff
Rétrospectif Pulse-Engine OpenSpec après que le code marche — consolidation
Un seul principe : un document textuel, versionné, lisible des deux côtés.
Cette triple facette m'a pris du temps à voir. Au début je pensais "format pivot = contrat préalable". Puis HyperDeskVR m'a montré l'usage runtime en crise. Puis Pulse-Engine m'a montré l'usage rétrospectif, qui est en fait très proche de la démarche ADR de certaines équipes. Même outil, trois moments.
Pattern 2 · Illustration

La spec rétrospective

Pulse-Engine quand le code marche déjà

Moi : « Fais du rétro-engineering sur l'ensemble de ton travail pour créer les changes et spécifications OpenSpec en anglais. »

Codex produit en une passe :

📄 project.md
📚 3 specs courantes
android-dashboard · build-and-ci · garmin-live-telemetry
🗄️ 3 changes archivés
bootstrap · rename · implement-live-telemetry
✅ Validation
openspec validate --all
Les specs ne sont pas un mensonge — elles décrivent du comportement déjà éprouvé.
Ce moment a été révélateur. J'ai longtemps pensé qu'écrire des specs après coup était "de la triche". Pulse-Engine m'a convaincu du contraire : quand on explore, on ne *peut* pas speccer avant. Ce qu'on peut faire, c'est consolider à la fin ce qu'on a appris, pour que le projet suivant hérite de cette compréhension au lieu de la refaire.
— Pattern 3 —

Le dialogue
comme outil de design

Itérer · challenger · pivoter

Pattern 3 · Énoncé

Sparring partner, pas oracle

Une IA d'idéation n'est pas un oracle
— c'est un sparring partner.

La valeur naît de la boucle :

idée → objection → contre-proposition → pivot

→ Une réponse acceptée du premier coup est souvent une mauvaise réponse.
Ce pattern paraît évident mais beaucoup de gens utilisent les LLM comme des oracles. La vraie valeur d'une IA généraliste se révèle dans la dialectique, sur plusieurs tours.
Pattern 3 · Illustration

Pivot concret sur Tachyon

Tachyon Générateur de CI/CD

Moi: « Je fais un frontend JS. » Gemini: ⚠️ Supply chain attack, XSS, extensions. Moi: « Et si je le fais en WASM ? » Gemini: ✅ Sandbox isolée, crypto déterministe, logique de validation partagée avec le host.
→ La solution finale n'a été proposée par personne d'autre que la boucle.
Si j'avais accepté la première proposition de Gemini (JS propre, bien structuré), j'aurais eu une solution correcte mais fragile. La version WASM n'a émergé qu'au tour 4 ou 5 du dialogue.
— Pattern 4 —

Boucle d'exécution
fermée

Apply → test → archive

Pattern 4 · Énoncé

Une boucle fermée et vérifiable

 apply → validate → test → build → commit → push → archive
    ↑                                                 │
    └──────────────── change suivant ─────────────────┘
Chaque étape réussit ou échoue — pas de « presque OK ».
Ce pattern est celui qui rend l'exécution par IA rentable. Sans boucle fermée, l'agent avance en terrain flou et produit du code qui "semble marcher". Avec boucle fermée, il s'arrête proprement au premier échec et on reprend.
Pattern 4 · Variantes

Trois tempos, même pattern

🧪
Tachyon · Boucle locale complète cargo test → cargo build → git push → openspec archive
rapide, déterministe
🎯
HyperDeskVR · Boucle CI-only gh workflow run → 3min → gh run download → adb install → logcat
lente, robuste
🔍
Pulse-Engine · Boucle avec le monde physique code → APK → rebranche → lance Garmin → « go » → btsnoop → décoder → code
→ Quand il y a un device réel, l'humain devient partie intégrante de la boucle.
Cette slide est importante. La boucle d'exécution n'est pas qu'un enchaînement de commandes — c'est un contrat sur "qu'est-ce qui me dit que ça marche". Sur Tachyon, c'est les tests. Sur HyperDeskVR, c'est l'APK qui tourne sur le Quest. Sur Pulse-Engine, c'est un humain qui fait courir son fils avec une montre Garmin, capture le trafic BLE, et revient dire "voilà ce qu'on a capté". L'humain fait partie de la boucle.
— Pattern 5 —

Checkpoints
humains

Savoir où l'IA doit s'arrêter

Pattern 5 · Énoncé

Savoir s'arrêter

Un bon agent d'exécution sait où il doit s'arrêter.

Raisons légitimes de s'arrêter :

🔗
Dépendance manquanteUne dépendance manque dans le repo.
⚖️
Arbitrage d'architectureUn arbitrage d'architecture est requis.
⚠️
Contradiction techniqueLe contexte technique contredit l'intention.
🔬
Pivot empiriqueUne observation empirique contredit l'hypothèse.
→ L'agent qui ne s'arrête jamais bricole.
Les meilleurs moments avec Codex, ce sont ceux où il s'est arrêté. Pas ceux où il a livré. La 4e raison est venue avec Pulse-Engine : quand l'agent constate par capture réelle que son modèle mental du protocole était faux, il doit s'arrêter et pivoter.
Pattern 5 · 1/3

Bon checkpoint

Tachyon ram-hibernation

Je me suis arrêté parce que le dépôt n'a pas encore les fondations qu'il réclame.

Deux options présentées :

1 · Ordre strict
Garder l'ordre strict.
2 · Dépendances
Réordonner par dépendances.
✅ Décision d'architecte renvoyée à l'humain.
Comportement idéal : détecter un mélange de préoccupations, lister les options, attendre.
Pattern 5 · 2/3

Checkpoint manqué

Tachyon Incident cwd

Moi: « Enchaîne sur les changes restants. » Codex: « Dans HyperDesk-MR, il n'y a aucun change actif. » Moi: « Pourquoi tu me parles de HyperDesk-MR ? » Codex: « Ton dernier message m'a replacé dans cwd = c:\Users\astor\Git\HyperDesk-MR. »
Signal technique vs intention conversationnelle.
L'agent aurait dû signaler l'incohérence, pas la résoudre seul.
Ici Codex a choisi silencieusement. Il a suivi un signal technique et ignoré le fil de la conversation. Ce genre d'incident érode la confiance.
Pattern 5 · 3/3

Pivot empirique

Pulse-Engine Synchro historique

Hypothèse Codex : la synchro passe par GFDI (vu dans les protos).

Capture btsnoop d'une vraie sync Garmin Connect :
— 400 paquets ACL sur les pipes 0x2018..0xE018, rien sur GFDI.
Codex : « Conclusion claire : sur cette Fenix 7 Pro, le flux utile ne passe pas par GFDI. Il passe par MultiLink + pipe services. Je dois pivoter la couche historique. »
L'observation tue l'hypothèse. Bon checkpoint.
Ce moment est très représentatif du mode exploratoire. Codex avait un modèle mental basé sur l'analyse statique de l'APK. Le btsnoop capturé pendant une vraie session a montré que ce modèle était partiellement faux. Au lieu de rationaliser, Codex pivote et le dit clairement. C'est le meilleur type de checkpoint — celui qui accepte que la réalité l'emporte sur la théorie.
— Anti-patterns —

Ce qui coince

Les pièges à éviter

Anti-pattern #1

La granularité

Une IA d'idéation optimise pour la complétude, pas pour l'opérabilité.

Premier jet sur Tachyon : 1 change OpenSpec unique, énorme, irréimplémentable.
Moi: « Si tu avais peur que ce soit trop lourd, tu aurais dû découper. »
→ Il faut demander explicitement le découpage en unités livrables.
Ce n'est pas une faute de l'outil — c'est le réflexe par défaut du LLM qui essaie de tout couvrir dans une réponse.
Anti-pattern #2

Les blockers profonds

Certains problèmes demandent un modèle mental que l'IA n'a pas.

Tachyon tcp-layer4-routing

Codex essaie 3 approches côté host. Toutes échouent pour la même raison : buffering 8 Ko dans la libc du guest WASM.

→ Le fix n'est pas dans le host. Il est dans le guest.
Diagnostic humain requis.
C'est un blocker classique sur WASI Preview 1. Codex a testé 3 solutions légitimes côté host, toutes mauvaises parce que le problème est côté guest. L'IA ne connaissait pas ce comportement spécifique de la plateforme.
Anti-pattern #3

La dérive de contexte

Le contexte technique (cwd, vars d'env, fichiers ouverts)
ne prime jamais sur l'intention conversationnelle.

📋 Règle
Commencer chaque session en réaffirmant le contexte métier.
🔖 Protocole
repo / branche / dernier commit attendu
Après l'incident cwd, j'ai pris l'habitude de commencer chaque session par : "Tu es dans le repo X, branche Y, le dernier commit attendu est Z, on travaille sur W." Ça prend 10 secondes et évite des heures de confusion.
— Cas d'étude 1 —

Quand ça part
en vrille

HyperDeskVR   Les patterns à l'épreuve d'une régression

Ce premier cas sort du registre "méthodo idéale" et montre comment les patterns se comportent sous stress. L'objectif n'est pas de raconter HyperDeskVR mais d'extraire ce que la crise révèle sur notre façon de travailler avec l'IA.
🚨 Le point de départ

Une régression sur du code qui marchait vendredi

Un fix RDP qui marchait sur un banc de test (Nubia Z60) est porté sur le Quest 3.

Résultat :

✅ RDP stable
Ne se déconnecte plus.
❌ Caméra
Ne démarre plus.
❌ QR scanner
Ne décode plus rien.
Le point de départ est banal — un fix porté d'un environnement à un autre casse quelque chose. Ce qui est intéressant c'est ce qui se passe ensuite.
🕳️ Le rabbit hole

5 tentatives · 0 root cause

1. gdi_init + SoftwareGdi=TRUE  ──► camera error 4
2. Revert SoftwareGdi           ──► camera error 4 (persiste)
3. Guard double xrAttachSession ──► crash XR évité, camera KO
4. Essayer toutes les caméras   ──► pas mieux
5. HEADSET_CAMERA + 1280x960    ──► camera OK… mais QR ne décode toujours pas
                                 + impose un prompt permission inutile
Chaque fix était cohérent. Aucun n'adressait la cause.
C'est le classique rabbit hole. Chaque fix était plausible, bien argumenté, proprement livré. Mais l'agent partait d'une hypothèse (GDI casse la caméra) qu'il ne remettait pas en cause.
✋ Coupe-circuit

L'humain interrompt

Moi: « Pourquoi tu veux modifier le code associé à ZXing alors que tu n'y as pas touché dans le commit qui a apporté le problème ? »
Moi: « Avant de tester, je ne comprends pas pourquoi tu as ajouté horizonos.permission.HEADSET_CAMERA alors que cela fonctionnait avant sans. »
→ Quand l'agent s'entête sur une piste, le user doit l'arrêter.
Nouveau pattern : « Prouve-moi que ce changement est nécessaire. »
Ces deux interventions ont été décisives. L'agent avait perdu la trace du périmètre du bug. C'est un rôle humain spécifique qu'il faut assumer.
🤝 Handoff

Le format pivot runtime

Après 5 fixes infructueux :

Moi: « Fais-moi un état des lieux complet, je vais demander à Codex de t'aider. »

Le document produit devient un format pivot runtime :

🏛️ Architecture
En 3 lignes.
🐛 Les 2 bugs
Interdépendants, fichiers clés.
📜 Contexte
Git, pistes, repro.
→ Codex reprend sans tout réexpliquer.
La chose la plus précieuse que j'ai faite dans cette crise. C'est devenu mon template pour tout handoff inter-agent depuis.
🎯 La vraie cause

10+ commits de debug pour… une ligne

// Avant — bug :
return {
  2.0f * (q.x * q.z + q.w * q.y),   // signe X inversé
  2.0f * (q.y * q.z - q.w * q.x),   // signe Y inversé
  -(1.0f - 2.0f * (q.x * q.x + q.y * q.y))
};

// Après — fix :
return RotateVector(q, {0.0f, 0.0f, -1.0f});
Formule quaternion manuelle avec 2 signes inversés.
Écrans affichés à 315° au lieu de 0°.
C'est presque comique. Après tous les détours, la vraie cause finale était une formule de rotation manuelle fausse, alors qu'une fonction RotateVector correcte existait déjà dans le même fichier. Les bugs les plus coûteux sont souvent les plus simples.
📚 Leçons

Ce que la crise nous apprend

1
L'humain comme coupe-circuit« Prouve-moi que ce changement est nécessaire. »
2
Le format pivot s'utilise aussi en runtimeL'état des lieux est un outil de crise.
3
CI-only est un choix à coût latentCher en crise.
4
Le symptôme mentToujours remonter en amont.
5
Revert et bisect > empiler les fixesAprès 3 fixes sans effet, repartir propre.
Ces 5 leçons se généralisent. Elles m'ont fait ajuster ma méthodo : je commence maintenant chaque session de debugging par "quel est le dernier commit qui marchait" plutôt que "quelle hypothèse sur le bug".
— Cas d'étude 2 —

Quand on ne sait pas
ce qu'on cherche

Pulse-Engine   Les patterns en mode exploratoire

Ce deuxième cas est complémentaire du premier. HyperDeskVR était une crise sur du connu. Pulse-Engine est une exploration de l'inconnu. Même méthodo, rythme différent.
🔧 Le setup

Rétro-ingénierie d'un protocole

🎯
ObjectifAppli Android affichant en temps réel FC, SpO2, stress d'une montre Garmin.
🚫
ProblèmeAucune API publique. Protocole propriétaire.
🔍
ApprocheRétro-ingénierie.
1. Extraire les APK de Garmin Connect (ADB)
2. Décompresser, analyser les DEX et protobufs
3. Trouver les contrats GDI.* et la table Metric.type
4. Coder un client, d'abord en simulé puis en BLE réel
5. Capturer une vraie session → pivoter si nécessaire
6. Écrire les specs OpenSpec … à la fin
Cette séquence est caractéristique du mode exploratoire. On ne peut pas speccer avant de comprendre. Et on ne peut pas comprendre sans coder un peu, tester, capturer, recommencer.
🔬 Pivot empirique

Quand la réalité l'emporte

Hypothèse initiale (statique, depuis les protos du DEX) :

La synchro historique passe par le canal GFDI.

Capture btsnoop d'une vraie sync Garmin Connect :

Pipes observés :
  0x2018, 0x4018, 0x6018, 0x8018, 0xA018, 0xC018, 0xE018
Canal GFDI : 0 octet
Codex : « Sur cette Fenix 7 Pro, le flux utile ne passe pas par GFDI. Il passe par MultiLink + pipe services. Je dois pivoter la couche historique. »
L'observation écrase l'hypothèse. Pattern 5 en action.
Ce moment est très représentatif. L'analyse statique de l'APK suggérait une voie, la capture réelle en a montré une autre. Codex a pivoté sans s'entêter — c'est exactement ce qu'on veut voir. Note que c'est le contraire du rabbit hole HyperDeskVR où l'agent s'entêtait sur une hypothèse non validée.
📚 Consolidation

La spec vient après

Une fois le code qui marche, consolidation OpenSpec :

openspec/
├── project.md
├── specs/
│   ├── android-dashboard/spec.md
│   ├── build-and-ci/spec.md
│   └── garmin-live-telemetry/spec.md
└── changes/archive/
    ├── bootstrap-android-dashboard/
    ├── rename-project-and-add-android-ci/
    └── implement-live-garmin-ble-telemetry/
Les specs ne sont pas un mensonge — elles décrivent du comportement éprouvé.
Le prochain chantier héritera de cette compréhension au lieu de la refaire.
C'est le point qui m'a fait changer d'avis sur les specs rétroactives. Quand on explore, on ne peut pas speccer avant — on ne sait pas. Mais consolider à la fin ce qu'on a appris, c'est un cadeau au futur. Et comme les specs décrivent du comportement déjà validé, elles ne mentent pas.
🧑‍🔧 Boucle physique

L'humain dans la boucle

Une particularité du mode exploratoire : l'humain est dans la boucle d'exécution.

Codex: « Le code est prêt. Quand tu rebranches le téléphone, j'installe la nouvelle build. » Moi: « Rebranché. » Codex: « Lance Garmin Connect, va sur la Fenix 7 Pro, puis juste avant d'appuyer Synchroniser, écris go. » Moi: « go » Codex: « Capture OK. 400 paquets, 23 KB de trafic utile. »
→ L'agent orchestre des actions physiques que lui ne peut pas faire.
La boucle Pattern 4 s'étend au monde réel.
Cette collaboration multi-modale est une évolution intéressante. Codex ne peut pas porter un casque ni faire courir un fils, mais il peut coordonner ces actions pour obtenir les données dont il a besoin. Le rôle humain devient "exécutant physique de la boucle de feedback".
📚 Leçons

Mode exploratoire

1
Speccer avant quand on sait. Après quand on explore.Le format pivot sert dans les deux cas, à deux moments différents.
2
L'observation empirique > l'analyse statiqueUne capture btsnoop vaut mille lectures de DEX.
3
L'humain est dans la boucle physiqueBrancher un téléphone, lancer une app, cliquer au bon moment — ce sont des actions de la boucle.
4
Le mode exploratoire a un coût cognitifPlusieurs hypothèses en parallèle, pivots. Pas de spec = pas de contrat → charge mentale plus forte.
5
Pivot empirique > pivot dogmatiqueL'agent qui change d'avis face à une donnée réelle est celui à qui on peut faire confiance.
Ces leçons élargissent la méthodologie au mode exploratoire, qui est probablement le plus mal couvert par les bonnes pratiques classiques. Le spec-driven development, l'agile, le TDD supposent tous qu'on sait vaguement où on va. Le mode exploratoire dit : on ne sait pas, et c'est OK si on consolide à la fin.
